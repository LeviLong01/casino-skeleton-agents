# Elevated player bust/loss rate for aggressive_20 vs standard_17 pairing

- **Pairing:** aggressive_20 vs standard_17
- **Severity:** low
- **Detected:** 20260819T200646Z

## Evidence
Observed over 50 rounds: bust=68.0% (ceiling 40%), win=24.0% (expected range 30%-55%), loss=70.0%, push=6.0%. Source: AggressivePlayerStrategy.should_hit returns True while hand.value() < 20, causing hits on 17/18/19-value hands that standard strategy (and the monitor's baseline expectations) would treat as stand points; Table.play_round awards the round to 'dealer' immediately upon player_hand.is_bust() without evaluating the dealer's hand.

## Likely cause
This is expected behavior, not a genuine anomaly. The `AggressivePlayerStrategy` (aggressive_20) is explicitly documented in casino/strategies.py as "Deliberately over-aggressive: kept in the strategy library as a stress-test fixture so the anomaly monitor has real, occasional signal to react to." It hits until hand value reaches 20 (`hand.value() < 20`), meaning the player keeps drawing on hands worth 17, 18, and 19 - values that a normal player would stand on. Since roughly 30-40% of all two-card starting hands already fall in the 12-19 range, and this strategy continues hitting through 17-19, it drives the player hand well past the safe drawing threshold, mathematically inflating the bust probability far above the 40% ceiling calibrated for basic/standard strategies. The resulting high bust rate directly suppresses the win rate (since a player bust in `play_round` immediately awards the round to the dealer regardless of the dealer's eventual hand), explaining both breached thresholds simultaneously.

## Recommendation
No code fix required for correctness — confirm with the team that aggressive_20 is intentionally deployed only as a stress-test/fixture strategy and not accidentally enabled in production-facing tables. If it should not trigger alerts, add it to the anomaly monitor's exclusion/allowlist (or use strategy-pair-specific thresholds) so aggressive_20 vs standard_17 pairings don't repeatedly fire false-positive incidents. If it was mistakenly enabled for live play, replace it with BasicPlayerStrategy (basic_17) at the table configuration level.
