# Elevated player win rate (58%) for basic_17 vs standard_17 — likely small-sample statistical noise, not an engine defect

- **Pairing:** basic_17 vs standard_17
- **Severity:** low
- **Detected:** 20260819T202035Z

## Evidence
Flagged pairing basic_17 vs standard_17 over 50 rounds: win=58.0% (breaches expected 30%-55% band), loss=32.0%, push=10.0%, player bust=14.0%. n=50 is small enough that a swing of this size (≈13 points above the ~45% expected midpoint) falls within ~2 standard errors (SE≈7pp for p≈0.45, n=50), and the correspondingly low 14% bust rate (vs. the ~28% typically expected for a hit-under-17 player against a hit-under-17 dealer) supports a favorable run of hands rather than a systematic scoring/logic bug in Table, Hand, or the strategy classes.

## Likely cause
Both PlayerStrategy.basic_17 and DealerStrategy.standard_17 implement the identical rule (hit while hand value < 17, stand otherwise), and Table.play_round() correctly applies standard blackjack sequencing: player acts first and busts are resolved before the dealer draws, then higher/lower/tie determines winner. Nothing in table.py, strategies.py, or hand.py shows a logic error that would systematically favor the player (e.g., outcome assignment, ace-counting in Hand.value(), and bust checks are all correct). Because both sides use the exact same 'hit under 17' rule, the theoretical player win rate should sit modestly *below* 50% (classic house edge from the player busting first), which is presumably why the monitor's expected band is 30%–55%. A 58% win rate over only 50 rounds is well within the range of normal sampling variance for a Bernoulli-like win/loss process at this sample size — the standard error on a ~45% true win rate at n=50 is roughly ±7 percentage points, meaning a result of 58% is only ~1.8–2 standard errors from the expected mean, not a strong statistical outlier. The unusually low bust rate (14% vs. a more typical ~28% for a 'hit until 17' player) is consistent with this small-sample variance rather than a code defect — a lucky run of high starting hands would suppress busts and inflate win rate simultaneously.

## Recommendation
Before treating this as a real engine bug, re-run the basic_17 vs standard_17 pairing for a much larger sample (e.g., 5,000–10,000 rounds) and recompute win/loss/push/bust rates with confidence intervals; if the win rate reverts toward the 42-48% range, this confirms it was sampling noise and no code change is needed. Separately, harden the anomaly monitor to use sample-size-aware thresholds (e.g., a z-test or Wilson confidence interval around the expected win rate) instead of a fixed 30%-55% band, so that n=50 samples don't trigger false-positive alerts. As a sanity check, also verify Deck's shuffle/draw implementation (not shown here) isn't introducing any bias in card order that could correlate with dealer/player draw sequencing.
