# Low player win-rate alert for basic_17 vs standard_17 likely statistical noise, not a code defect

- **Pairing:** basic_17 vs standard_17
- **Severity:** low
- **Detected:** 20260820T022325Z

## Evidence
Observed over 50 rounds: win=26.0%, loss=62.0%, push=12.0%, bust=40.0%; monitor flagged win rate 26.0% as outside the expected 30%-55% band. Sample size n=50 gives an approximate standard error of ~6-7 points on the win-rate estimate, meaning the expected-range check has limited statistical power at this sample size and a single unlucky run can trip the threshold even when strategy logic is unchanged and correctly implemented (should_hit thresholds of <17 for both BasicPlayerStrategy and StandardDealerStrategy, standard Hand.value()/is_bust() ace handling).

## Likely cause
The game logic in table.py/hand.py/strategies.py implements standard blackjack rules correctly: BasicPlayerStrategy hits until hand value >= 17 (a reasonable "mimic the dealer" style strategy), the dealer strategy is identical (hit < 17), and the player acts first, so a player bust ends the round immediately in the dealer's favor even if the dealer would also have busted. This is the normal house-edge mechanic of blackjack, not a bug. Published simulation results for a 'stand on 17, no bust-avoidance, no dealer-upcard awareness' player strategy against a standard dealer typically show a win rate in the high-30s to low-40s percent, with meaningfully higher loss rates due to the player-acts-first asymmetry. With only 50 rounds sampled, the binomial standard error on the win rate is roughly 6-7 percentage points, so a realistic true win rate of ~35-40% can easily produce an observed 26% win rate by chance. There is no logic path in play_round(), should_hit(), or Hand.value()/is_bust() that would systematically suppress player wins beyond the expected house-edge effect (e.g., no double-counting of busts, no incorrect ace handling, no asymmetric push/blackjack payout logic visible). The 40% bust rate, while on the high side, is consistent with sampling variance rather than an obvious defect like a broken ace-reduction loop or an off-by-one in the hit threshold.

## Recommendation
Before treating this as a code regression, re-run the basic_17 vs standard_17 matchup for a much larger sample (e.g., 5,000-10,000 rounds) to get a statistically stable win-rate estimate and compare it against the theoretical baseline for this exact strategy pairing. If the win rate remains below ~30% at high N, then audit play_round() and Hand.value() for a real defect (e.g., ace reduction, bust ordering, deck reshuffling with num_decks). If it converges back into range, treat this alert as a false positive and widen/recalibrate the expected-range thresholds (or require a minimum sample size) for low-N monitoring windows so single 50-round batches don't trigger alerts on normal variance.
