# Elevated bust/loss rate for aggressive_20 vs standard_17 — expected behavior of stress-test fixture, not a system fault

- **Pairing:** aggressive_20 vs standard_17
- **Severity:** low
- **Detected:** 20260820T024302Z

## Evidence
Over 50 rounds: bust=68.0% (ceiling 40%), win=22.0% (expected range 30%-55%), loss=72.0%, push=6.0%. The player strategy in play is aggressive_20 (hits while hand.value() < 20), directly correlating with the abnormally high bust/loss rates.

## Likely cause
The player strategy in this pairing is AggressivePlayerStrategy (name="aggressive_20"), whose should_hit() logic hits on any hand value < 20 (casino/strategies.py). This is far more aggressive than basic strategy (hit < 17) and, combined with Hand.value()'s standard blackjack scoring (casino/hand.py), causes the player to draw additional cards on hand totals of 17, 18, and 19 — totals that are normally held. Drawing on these already-strong totals mathematically drives up the probability of busting (going over 21) on nearly every hit past 17, since roughly 9 of 13 ranks (7,8,9,10,J,Q,K, plus some A cases when re-drawing) risk pushing an existing 17-19 total over 21. Table.play_round() immediately resolves the round as a dealer win the moment player_hand.is_bust() is true, so a strategy that structurally forces extra hits on strong hands will produce a bust rate well above the 40% ceiling and a correspondingly depressed win rate. Notably, the code comment on AggressivePlayerStrategy explicitly states it is "deliberately over-aggressive... kept in the strategy library as a stress-test fixture so the anomaly monitor has real, occasional signal to react to" — indicating this pairing is intentionally engineered to trip these exact thresholds.

## Recommendation
Confirm with the team whether aggressive_20 vs standard_17 is intentionally included in live/monitored strategy rotations or is meant to be confined to isolated stress-test runs. If it's only a test fixture, exclude this pairing from the anomaly monitor's active alerting scope (e.g., tag/allowlist it) so it doesn't generate paging incidents. If it is meant to represent a real player behavior under evaluation, no code fix is needed — the metrics reflect correct simulation of a known bad strategy; treat this as confirmation that the monitor's thresholds are working rather than a bug in table.py/hand.py/strategies.py.
