# Elevated player bust rate for aggressive_20 vs standard_17 pairing

- **Pairing:** aggressive_20 vs standard_17
- **Severity:** low
- **Detected:** 20260820T020002Z

## Evidence
Over 50 rounds: win=28.0% (below expected range 30%-55%), loss=68.0%, push=4.0%, bust=66.0% (exceeds ceiling of 40%). The bust rate breach (66% vs 40% ceiling) and low win rate breach (28% vs 30-55% range) are directly attributable to AggressivePlayerStrategy.should_hit() returning True for any hand value < 20, versus the standard 17-stop threshold used elsewhere in the codebase (BasicPlayerStrategy, StandardDealerStrategy).

## Likely cause
The player strategy in this pairing is AggressivePlayerStrategy (name="aggressive_20"), whose should_hit() logic keeps hitting as long as hand.value() < 20. This means the player will hit on any hand totaling 17, 18, or 19 — hand totals where, with a standard 52-card deck (Deck) and Hand.value()'s ace-adjustment logic, the probability of drawing a card that pushes the total past 21 is very high (roughly 50-70% depending on soft/hard totals). Table.play_round() immediately resolves any player hand that busts as a loss for the player (winner="dealer") before the dealer even draws. Consequently this strategy is expected, by design, to produce bust rates far above a normal 17-stop strategy (~40% ceiling) and depressed win rates, since a large fraction of rounds never reach a fair value comparison against the dealer. The source code explicitly documents AggressivePlayerStrategy as 'deliberately over-aggressive... kept as a stress-test fixture so the anomaly monitor has real, occasional signal to react to,' confirming this is intentional simulated behavior rather than a bug in Table, Hand, or Deck logic.

## Recommendation
Confirm this is expected/simulated stress-test behavior rather than a live-table misconfiguration: verify in the monitor's config/scheduler that 'aggressive_20' is only ever paired intentionally for fixture/testing purposes and is not accidentally being used as a live player strategy in production. If it is only a test fixture as the code comment states, suppress or re-classify alerts for this specific strategy pairing (e.g., add it to an allowlist/exception list in the anomaly monitor) so it doesn't continue to generate false-positive incident reports; if it is unexpectedly active in production play, disable/remove AggressivePlayerStrategy from the active strategy pool immediately.
